## 📌 Project Overview

This repository contains the complete implementation for the ConsultBae AI Automation technical assessment across all 5 tasks:

1. **Task 1: Disjoint-Set Entity Resolution Pipeline (`task1_merge/`):** Normalizes, deduplicates, and resolves multi-source candidate profiles across messy datasets (Naukri applicants, Gig platforms, CRM contacts) using Disjoint-Set Union (Union-Find) with deterministic key matching and quarantined fuzzy review.
2. **Task 2: No-Code Automation in n8n:** Built 100% in n8n (demonstrated in video):
   * **Primary Flow (Option 1):** Ingests candidate CSV batches via webhook, cleans identifiers, queries the Task 1 SQLite database (`consultbae_merged.db`), detects duplicate applicants, and dispatches email alerts.
   * **Bonus Flow (AI Resume Screening):** Ingests PDF resumes via webhook, extracts text, leverages a **Basic LLM Chain** with **Google Gemini Chat Model** to categorize candidate skills (`automation-heavy`, `web-dev`, `data-ai`), calculates a 1–100 fit score, and routes qualified applicants into destination sheets.
3. **Task 3: Mini Audio Collection Web Application (`task3_audio_app/`):** A full-stack web application allowing applicants to enter contact info and either record voice introductions in-browser (`MediaRecorder` API) or upload pre-recorded audio files. The FastAPI backend automatically extracts acoustic metadata (duration, sample rate in kHz, bitrate, RMS dBFS loudness, and noise crest factor) and dynamically links submissions to Task 1 candidate records.
4. **Task 4: Data Quality & Entity Resolution Report (`task4_data_issues.md`):** Comprehensive catalog of all data anomalies discovered across the raw CSVs with concrete evidence, normalization rules, and remediation rationales.
5. **Task 5: High-Concurrency Scaling Analysis (`task5_scale_analysis.md`):** Architectural blueprint and bottleneck mitigation plan for scaling the audio collection system to 5,000+ gig workers with presigned S3 direct uploads, async worker queues, and PostgreSQL atomic upserts.

#### 🌟 Primary Flow (Option 1): CSV Ingestion & Duplicate Candidate Detection

**Workflow Architecture:**
```
[Webhook (POST /check-duplicates)]
                 │
                 ▼
     [Extract from CSV Node]
                 │
                 ▼
[Edit Fields (Normalize)] (Lowers email, extracts 10-digit phone)
                 │
                 ▼
[SQLite Node (Execute Query)] (SELECT FROM persons WHERE canonical_email OR canonical_phone)
                 │
                 ▼
     [IF (Duplicate Detected?)]
       ├── TRUE  ──► [Send Email Alert Node] (Sends duplicate alert to talent-ops@consultbae.com)
       └── FALSE ──► [No-Op Node] (Passes clean new candidate)
```

**How Node Logic Works in n8n:**
1. **Webhook Trigger:** Listens for incoming CSV file uploads via `POST /check-duplicates`.
2. **Extract from CSV:** Parses raw binary CSV text into structured candidate items.
3. **Edit Fields:** Standardizes text and formats phone/email fields visually.
4. **SQLite Node:** Executes a parameterized query against `consultbae_merged.db`:
   ```sql
   SELECT person_id, canonical_name, canonical_email, canonical_phone, canonical_city, sources 
   FROM persons 
   WHERE (canonical_email IS NOT NULL AND canonical_email = $1)
      OR (canonical_phone IS NOT NULL AND canonical_phone = $2)
   LIMIT 1;
   ```
5. **IF Node:** Evaluates whether `person_id > 0`.
6. **Send Email Alert:** Constructs an automated email displaying candidate details alongside the matching existing profile.

**How to Test in n8n:**
1. Launch n8n: `npx n8n` (open `http://localhost:5678`).
2. Point the SQLite credentials to `consultbae_merged.db`.
3. Trigger the test webhook:
   ```bash
   curl -X POST "http://localhost:5678/webhook-test/check-duplicates" -F "file=@task2_test_candidates.csv"
   ```

#### 🚀 Bonus Flow: AI Resume Screening & Skill Categorization (PDF Ingestion)

**Workflow Architecture:**
```
[Webhook (POST /screen-resume)]
       │
       ▼
[Extract from File] (Extract from PDF)
       │
       ▼
[Edit Fields] (Manual field mapping)
       │
       ▼
[Basic LLM Chain] ◄── [Google Gemini Chat Model]
       │ (Skill extraction, category tagging & fit scoring)
       ▼
      [If] (Condition: is_qualified == true)
       ├── TRUE  ──► [Insert row] (Qualified Candidates Pool)
       └── FALSE ──► [Insert row1] (Review / Alternative Pool)
```

**How Node Logic Works in n8n:**
1. **Webhook:** Receives incoming candidate resume PDF binary payloads.
2. **Extract from File (PDF):** Extracts document text directly from the PDF.
3. **Edit Fields:** Maps candidate name, email, and phone metadata.
4. **Basic LLM Chain + Google Gemini:** Prompts Google Gemini to analyze technical experience, assign primary category tags (`automation-heavy`, `backend-engineering`, `web-dev`, `data-ai`), and compute a 1–100 fit score.
5. **If Node:** Checks if `fit_score >= 70`.
6. **Insert row / Insert row1:** Conditionally routes qualified candidates to the fast-track sheet and alternative applicants to the general review pool.

## 📊 Data Quality & Normalization Summary (Task 4)

| Anomaly Class | Raw Evidence / Examples | Remediation & Handling Strategy |
| :--- | :--- | :--- |
| **Phone Number Formats** | `+919000000254`, `919000000231`, `09000000287`, `+91-9000000131` | Stripped all non-digits, removed `91` and leading `0` prefixes, strictly validated 10-digit length. Invalid formats return `None`. |
| **City Name Variations** | `Bangalore` vs `Bengaluru`, `Gurgaon` vs `Gurugram`, `PUNE` vs `pune` | Alias dictionary mapping to canonical names; Title Casing applied. Distinct metro zones (`Delhi`, `New Delhi`, `Delhi NCR`) intentionally preserved. |
| **Intra-Source Duplicates** | `Rohit Verma` (`source1` L25 & L31), `Nikhil Chopra` with `alt.` email (L27 & L37) | Detected via `(email, phone)` indexing; linked into identical entity components via Union-Find without creating duplicate profiles. |
| **Column-Shifted Rows** | `source2` L20 had skill strings leaked into the `email_id` field | Validated email syntax (presence of `@`); flagged column-shifted rows, skipped invalid email keying, but preserved worker name and skills. |
| **Embedded Header Rows** | `source3` L16 repeated `Name, Phone Number, City, Verified...` as data | Header-key subset comparison; automatically skipped repeated header records. |
| **CTC Unit Ambiguity** | `7.8`, `12.5` (LPA decimals) vs full annual figures | Preserved verbatim text in `ctc_raw`; flagged `ctc_unit_suspect = 1` for values $< 200$ to prevent accidental silent conversion. |
| **City Relocation Conflicts** | Multi-source candidates with differing cities (e.g. `Noida` and `Delhi NCR`) | Concatenated distinct cities with pipe separators (`Noida \| Delhi NCR`) and set `city_conflict = 1` (5 candidates). |

## 🛠️ Stuck Log: Technical Deep-Dives

Below are the 3 hardest technical challenges encountered during this project, how they were resolved, and why specific alternatives were rejected.

---

### Stuck Point 1: Transitive Multi-Source Entity Resolution vs. Over-Merging on Fuzzy Fallbacks

#### The Problem
The three source datasets lacked a universal single primary key:
* `source1` had Name, Email, Phone, City, CTC, Skills.
* `source2` had Name, Email, Rate, City, Skills (NO Phone).
* `source3` had Name, Phone, City, Verified (NO Email).

Pairwise matching requires $O(N^2)$ cross-product joins and struggles to maintain transitive equivalence ($A \sim B \land B \sim C \implies A, B, C$ are the same person).

#### What Was Investigated & Tested
* Graph clustering libraries vs. custom Disjoint-Set Union (Union-Find).
* RapidFuzz similarity algorithms (`fuzz.ratio`, `fuzz.token_sort_ratio`).

#### What AI / Standard Tools Suggested
AI suggested applying an automated fuzzy threshold ($\text{score} \ge 80$) on `(Full Name, City)` directly inside the Union-Find loop so that any two records with similar names in the same city would automatically merge into one `person_id`.

#### Why That Suggestion Was Rejected
**High False-Positive Risk on Indian Names:** In Indian recruitment datasets, common name-surname combinations ("Arjun Mehta", "Manish Bhatia", "Divya Chopra") frequently belong to distinct individuals living in the same metropolitan area (e.g., Noida or Gurugram). Auto-merging on name+city conflated two completely different professionals (one a Python developer, another a frontend engineer) into a single profile. Silent false merges are irreversible and poison downstream recruiter outreach.

#### How I Got Unstuck
1. **Implemented Disjoint-Set Union (Union-Find) for Deterministic Merges:** Built a clean `UnionFind` class with path compression and union-by-rank. Hard merges are executed *strictly* on verified unique identifiers (canonical 10-digit phone and canonical lowercased email). This resolved multi-source transitive chains in $O(N \cdot \alpha(N))$ time.
2. **Quarantined Fuzzy Candidates to `needs_review`:** Rather than auto-merging on fuzzy similarity, any singleton pairs with high name+city similarity ($\ge 85$) are written to a dedicated `needs_review` table with side-by-side attributes and match reasoning for recruiter review.

---

### Stuck Point 2: CTC Unit Ambiguity & Currency Multiplier Hazards (LPA vs. Absolute Rupees)

#### The Problem
In `source1_naukri_applicants.csv`, the `Current CTC` column had severe unit discrepancies:
* Some candidates had decimal values: `7.8`, `12.5`, `24.0`.
* Others had integer numbers representing Lakhs or absolute figures.

#### What Was Investigated & Tested
* Surveying recruitment ETL patterns and salary distribution histograms.
* Hard cutoff evaluations (e.g., `< 100` implies LPA).

#### What AI / Standard Tools Suggested
AI suggested applying an in-place conversion lambda multiplying values $< 100$ by $100,000$.

#### Why That Suggestion Was Rejected
**Silent Data Corruption Risk:** Blindly multiplying by $100,000$ destroys data provenance. If an applicant entered `15` representing 15,000/month stipend, or if a contractor entered daily/hourly figures, auto-converting to 1,500,000 INR creates fictitious executive compensation figures.

#### How I Got Unstuck
1. **Preserved Raw Verbatim Values:** Kept `ctc_raw` exactly as provided in the source file to maintain 100% auditability.
2. **Created an Anomaly Flag Column:** Implemented `flag_ctc_suspect()` to set `ctc_unit_suspect = 1` for values $< 200$ to explicitly flag decimal LPA formats for recruiter verification on the UI without altering underlying data.

---

### Stuck Point 3: Cross-Platform FFmpeg Resolution & Shared Normalization in FastAPI

#### The Problem
When implementing the Task 3 FastAPI audio app:
1. `pydub` relies on an external FFmpeg system binary. On environments without FFmpeg in system `PATH`, audio ingestion threw `FileNotFoundError: [WinError 2]`.
2. Phone normalization logic needed to match Task 1's normalization rules *identically* so walk-in applicants would accurately match existing profiles in `consultbae.db`.

#### What Was Investigated & Tested
* Static FFmpeg binary bundling vs. lightweight Python wrappers.
* Cross-module Python path resolution across `task1_merge/` and `task3_audio_app/`.

#### What AI / Standard Tools Suggested
* AI suggested committing a 100MB static `ffmpeg.exe` binary directly into the git repository.
* AI also suggested copy-pasting the `normalise_phone()` regex function into `task3_audio_app/main.py`.

#### Why That Suggestion Was Rejected
* Committing OS-specific binaries bloats git history and fails on Linux/macOS deployment targets.
* Copy-pasting business logic violates the DRY principle and leads to silent drift over time.

#### How I Got Unstuck
1. **Zero-Config FFmpeg Discovery with `imageio-ffmpeg`:** Added an automatic fallback bootstrap in `task3_audio_app/main.py` that checks for system `ffmpeg`. If missing, it dynamically fetches the platform-specific binary via `imageio_ffmpeg.get_ffmpeg_exe()` and injects it into `pydub.AudioSegment.converter` at runtime.
2. **Dynamic Path-Safe Module Import with Fallback Warning:** Added `TASK1_DIR` to `sys.path` to import `normalise_phone` directly from `task1_merge.merge_pipeline`.

## 📈 Scalability Blueprint (Task 5 Summary)

For launching to **5,000 gig workers** over a 48-hour campaign:
* **Decoupled Architecture:** Client requests presigned S3 upload URLs; audio streams directly to AWS S3 / Cloudflare R2 without burdening the application server.
* **Async FFmpeg Processing:** S3 upload triggers an SQS event consumed by Celery / AWS Lambda workers for non-blocking loudness/noise analysis.
* **Database Concurrency:** Migrate SQLite to AWS RDS PostgreSQL with `UNIQUE (canonical_phone)` and atomic `ON CONFLICT DO UPDATE` upserts to eliminate duplicate candidate race conditions.
* **Estimated 48-Hour Campaign Cloud Cost:** **< $5.00 total** (2.5 GB storage + Lambda compute + burstable PostgreSQL).
